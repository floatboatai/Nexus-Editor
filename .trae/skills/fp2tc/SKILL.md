# 功能点→测试用例生成+增强（fp2tc — Nexus_Editor 适配版）

## 铁律（全程不可违反）

1. **仅显式触发**，禁止通过关键词自动触发
2. **禁止同时加载超过2个源码文件到同一上下文**
3. **每个子智能体只处理1个一级功能点**，处理完立即结束
4. **基础用例生成后必须保存到文件**，不留在上下文中
5. **源码查询必须先用 Grep 定位**，再精确读取行范围
6. **设计规范使用摘要版**（下方内嵌），不读完整 references/test-patterns.md
7. **一级功能点超过10个二级功能点时**，提示用户分批处理
8. **子智能体并行数量不超过3个**
9. **用户回答"待定"时仍生成用例**，标注为"待确认"
10. **子智能体不写进度报告** — 子智能体只返回 `<<<STATS>>>` 结构化统计块给主会话。所有进度报告文件由主会话集中写入。
11. **用例文件必须先展示摘要让用户确认后**，才保存到磁盘
12. **前置条件的4要素缺一不可**，尤其"setup 代码"必须分步骤详细描述（每步含 import 语句 + 编辑器初始化 + 初始 markdown），禁止省略为仅给出函数签名。如果依赖特定插件或状态，setup 必须包含完整的插件加载和状态构造代码，使测试能直接执行
13. **阶段检查清单(Checklist)硬阻断** — Step A3 和 Step B4 的检查清单中所有项必须 ✅ 才能进入下一阶段。任何 ⬜ 项必须先补齐，禁止跳过。

## 输入参数

| 参数 | 必填 | 说明 |
|------|------|------|
| 功能点文档路径 | 是 | req2fp 生成的功能点文件路径（`test/function_points/FP-<change-id>-功能点.md`） |
| 需求文档路径 | 否 | 不提供时从功能点文档的"需求源索引"推断（openspec spec.md / prd.md） |
| 执行模式 | 是 | 1=完整流程 / 2=仅生成基础用例 / 3=仅增强用例 |
| 指定功能点 | 否 | 指定只处理某个一级功能点，不提供则处理全部 |

## 设计规范摘要（内嵌，不读完整文件）

````markdown
## 用例类型
- [正常] 合法输入标准操作，每个公开 API 至少1个
- [异常] 无效输入/违规操作/缺前置条件，每个必填参数至少1个
- [边界] 空文档、极端输入、超大文档、嵌套格式
- [等价类] 有效等价类1个+无效等价类各1个
- [流程] 多步骤编辑流程正向+关键撤销回退
- [数据] 解析正确性、AST 结构、round-trip 无损、事件触发

## 用例数量
- 简单功能点（1-2参数/单一行为）: 5-8个
- 中等功能点（3-5参数/组合行为）: 8-10个
- 复杂功能点（5+参数或多步骤交互）: 10-20个
- 每个用例步骤不超过5步（多步骤流程除外）

## 优先级比例
P1核心正向25% / P2基本正向20% / P3核心异常30% / P4边界条件20% / P5低频5%

## 编号规则
FP-{全局批次序号}-{二级序号}-{类型后缀}{序号}
全局批次序号: 由Step A1统一分配，每个一级功能点一个唯一序号（从01开始递增）
二级序号: 该一级功能点内的二级功能点序号（从01开始）
类型后缀: N正常/E异常/B边界/F流程/D数据
示例: FP-01-01-N01, FP-01-02-E01, FP-02-01-B01
⚠️ 全局批次序号必须在Step A1阶段预先分配，禁止每个批次独立从01开始编号

## 测试框架判定规则（由功能点类型标签自动推荐）
| 类型标签 | 推荐框架 | 理由 |
|---------|---------|------|
| [API契约] [AST解析] | Vitest | 纯逻辑，无需 DOM 交互 |
| [编辑交互] | Vitest | jsdom + CM6 dispatch |
| [Live Preview] | Vitest | Decoration / DOM 查询 |
| [插件能力] | Vitest | 插件注册逻辑 |
| [数据IO] | Playwright | Electron 文件系统 |
| [无障碍] | Vitest | ARIA 查询（jsdom）；真实键盘交互可选用 Playwright |
| [安全] | Vitest | XSS 注入测试 |
| [性能] | Vitest | 大文档 benchmark |
多标签时: 若含[数据IO]或[无障碍]且同时含其他标签，可拆分为多个用例分别用不同框架

## 步骤格式（三列式）
| 步骤 | 操作 | 预期结果 | 自动化信息 |
|------|------|---------|-----------|

## 断言标记（融入预期结果列）
[API] EditorAPI 方法返回值 → 验证方式
[AST] mdast 节点结构/类型 → 验证方式
[DOM] CM6 DOM 元素（.cm-editor/.cm-content/Widget）→ 验证方式
[STATE] 编辑器状态流转（selection/dispatch/editing flag）→ 验证方式
[CALC] 计算结果（字数统计/表格列数等）→ 验证方式
[EVENT] 事件回调触发（onChange/onFocus/onBlur）→ 验证方式

## 自动化信息列格式
基础阶段: 待增强
增强后: import: {import路径}; API: {方法名}({参数}); 框架: {vitest|playwright}; 等待: {条件}
注意: 使用分号(;)分隔，避免与Markdown表格管道符冲突

## 测试数据命名
TEST_{YYYYMMDDHHmm}_{描述}
时间占位符: {YYYY} {MM} {DD} {HH} {mm} {ss} {YYYYMMDD} {YYYYMMDDHHmm}
用于测试用的 markdown 文档内容也使用占位符避免硬编码

## 前置条件4要素（⚠️ 缺一不可，违反视为生成失败）
- 依赖环境: jsdom（Vitest默认）/ Electron demo（Playwright）
- 初始文档: 起始 markdown 内容（含具体值，如 "# Hello World"）
- 插件配置: 需要加载的 plugin 列表（如 plugin-slash, plugin-history）
- setup 代码: 分步骤详细描述，每步必须含:
  - import 语句: 从哪个包导入（如 `import { createEditor } from "@floatboat/nexus-core"`）
  - 编辑器初始化: createEditor 参数（container, initialValue, plugins, readOnly 等）
  - 状态构造: 如需特定状态，dispatch 或 API 调用序列
  - ⚠️ 禁止仅写"createEditor({...})"而不给出完整参数和 import
  - setup 代码必须使 vitest/playwright 能直接执行，无需额外推断

## 编辑器库特有规则
- 每个公开 API 方法至少1个正常用例 + 1个异常用例
- CM6 交互需注意 editing flag 生命周期（参见 AGENTS.md Table Widget 规则）
- Live Preview 测试需注意光标位置感知（光标进入/离开触发不同 Decoration）
- AST 测试需验证 round-trip 无损（parse → serialize → parse 一致）
- 插件测试需覆盖三层扩展点（Tier1 shortcuts/slashCommands/commands/handlers, Tier2 remarkPlugins/widgets, Tier3 cmExtensions）
````

## 执行流程

### Step -1: 加载历史教训（Self-Improving）

读取教训存储目录，将历史教训注入本次执行上下文。

1. 检查 `~/self-improving/` 是否存在 → 不存在则跳过（首次执行）
2. 读取 `~/self-improving/memory.md`（HOT层，跨技能通用教训）
3. 读取 `~/self-improving/domains/fp2tc.md`（测试用例生成专属教训）
4. 读取 `~/self-improving/corrections.md`，检查是否有计数≥2的待注入教训
   → 有则 AskUserQuestion 提醒用户："教训'XXX'已出现2次，是否在本次执行前先注入技能本体？"
5. 输出摘要："已加载 N 条通用教训 + M 条测试用例专属教训 + K 条待确认教训"

⚠️ 读取到的教训在本轮执行中与铁律同等效力。特别注意：教训中涉及子智能体的规则必须写入子智能体Prompt模板。注：Self-Improving教训文件（~/self-improving/）不计入铁律2的源码文件限制。

### Step 0: 启动 & 模式选择 & 环境校验

1. 询问用户选择执行模式:
   - `1. 完整流程（基础用例 → 增强）`
   - `2. 仅基础用例（不增强）`
   - `3. 仅增强（已有基础用例）`
2. 读取功能点文档，解析 change-id 和一级/二级功能点数量
3. 展示输入文档确认表:
   ```

   1. 功能点文档: ✅ {文件名} ({字符数}字符, {一级功能点数}个一级功能点, {二级功能点数}个二级功能点)
   2. 需求文档: ✅/⚠️ {自动推断路径或提示选择}
   3. 用例设计规范: ✅ 内置摘要
   4. 源码知识源: ✅ packages/ ({包数}个包, 可 Grep 搜索)

   ❓ 是否有其他输入文档需要补充？
   ```
   等待用户确认或补充
4. 源码包校验:
   - 扫描 `packages/` 下的实际包列表
   - 从功能点文档的类型标签推断涉及的包（如 [编辑交互] → core, [插件能力] → plugin-*）
   - 展示识别结果:
     ```
     🔍 源码包关联识别结果

     主包: packages/{主包}/

     关联包（自动识别）:
     - packages/{包名}/ ← 功能点文档中出现"{关键词}"关键词 {次数}次

     不关联的包:
     - packages/{包名}/ (无关键词匹配)

     ❓ 识别结果是否正确？是否需要手动补充？
     ```
   - 用户确认
5. 上下文预估 + 分批建议
   - 二级功能点总数>50时提示分批
   - 展示预估上下文占用
6. 用户确认"是否开始" → 根据模式进入对应阶段

### 阶段A: 基础用例生成（主会话循环）

**上下文策略**: 每次只加载1个一级功能点 + 对应需求文档章节，生成后保存文件释放上下文。

**Step A1**: 解析功能点文档结构 + 全局编号分配
- 提取所有一级功能点标题和二级功能点表格
- 按"需求源索引"定位 openspec spec.md / prd.md 的对应章节
- **全局编号分配**: 为每个一级功能点分配唯一的全局批次序号（01, 02, 03...），展示编号分配表:
  ```
  📋 全局编号分配表
  批次序号 | 一级功能点名 | 二级功能点数 | 推荐测试框架
  ──────────────────────────────────────────────
  01       | {名称}      | {数量}       | {Vitest/Playwright}
  02       | {名称}      | {数量}       | {Vitest/Playwright}
  ...
  ```
- 生成分批计划（每个一级功能点为1批，携带全局批次序号）

**Step A2**: 逐批生成基础用例

对每个一级功能点（每批，使用Step A1分配的全局批次序号）:
a. 精确切片读取该一级功能点的二级功能点表格
b. 精确切片读取 openspec spec.md / prd.md 对应章节（按"需求源索引"定位）
c. 使用上方内嵌的设计规范摘要
d. 为该一级功能点下的每个二级功能点生成测试用例
   ⚠️ **编号必须使用全局批次序号**，如当前批次是第2个一级功能点，则编号为FP-02-{YY}-{类型}{序号}，禁止重新从FP-01开始
e. **根据类型标签自动判定测试框架**（见设计规范摘要中的"测试框架判定规则"）

用例数量规则:
- 简单(1-2参数): 5-8个用例
- 中等(3-5参数): 8-10个用例
- 复杂(5+参数或多步骤): 10-20个用例
- 优先级按比例分配（P1 25%/P2 20%/P3 30%/P4 20%/P5 5%）

用例格式:
```markdown

  ```typescript

- [{标记}] {断言内容}
```

f. 该批所有用例生成完毕后展示统计摘要
g. 保存到文件: `test/testcases/{模块名}/CASE-{一级功能点名}/CASE-{一级功能点名}-测试用例.md`
h. **子智能体返回结构化统计**（⚠️ 子智能体不写进度报告文件，只返回数据给主会话）:
   在子智能体的 Task Prompt 中要求: 用例保存完成后，在返回消息末尾输出统计块:

   ```

   {
     "fp_number": "FP-{XX}",
     "fp_name": "{一级功能点名}",
     "secondary_fp_count": {二级功能点数},
     "case_count": {用例数},

   - ⚠️ **子智能体禁止写入进度报告文件**。只返回上述统计块。
   - ⚠️ 子智能体不得自行计算合计行。
   - ⚠️ **上下文保护**: 禁止在 `<<<END_STATS>>>` 之后输出任何额外内容。保存的用例文件内容禁止出现在返回消息中。
i. 释放上下文

**Step A2.1**: 主会话收集统计 + 写入进度报告行（每批完成后）

### Step B5: 教训汇入+反思+注入闭环（Self-Improving）

#### B5.1 收集本轮问题
从以下来源收集：
- **自查反思**：首先通过本次执行的全过程回忆反思，反省出中断、没有按照SKILL.md执行、跳过执行步骤等状况，提取出本次执行过程中的教训
- 阶段A用例生成质量：用户纠正了用例格式/编号/数量/前置条件
- 阶段B增强质量：增强覆盖率低、import 路径错误、API 签名不匹配
- 子智能体问题：进度报告未写入、上下文超限、源码查询方式错误
- 用户纠正（对话中的"不对/应该是/错了"）
- 铁律违反：子智能体违反并行数量限制/源码查询限制

#### B5.2 记录到 corrections.md
每条问题按以下格式记录，检查是否已有同类教训：
```
## [日期] [教训标题]
- **来源**: 阶段A/B / 子智能体 / 用户纠正 / 铁律违反
- **现象**: 具体发生了什么
- **教训**: 以后应该怎么做
- **分类**: 用例生成 / 源码增强 / 子智能体管理 / 编号规则 / 前置条件 / Prompt质量
- **严重度**: 高（必崩）/ 中（可能出错）/ 低（偶发）
- **计数**: X/2
- **注入路径**: 待判定
- **状态**: 🔍观察中 / ⏳待注入 / ✅已注入
```
同类教训判断：标题相似或现象相同 → 计数+1。计数达到2/2则标记"⏳待注入"。

#### B5.3 判断注入路径
| 教训特征 | 注入路径 | 目标文件 |
|----------|---------|---------|
| "禁止做X"/"必须做Y"硬规则 | 路径A：铁律 | SKILL.md 铁律章节（从第14条起） |
| 操作经验/最佳实践 | 路径C：历史教训 | SKILL.md 历史教训与防复发规则章节 |
| AI分析质量（用例设计/增强规则） | 路径C：Prompt | SKILL.md 的设计规范摘要 或 子智能体Prompt模板 |
| 临时性/环境问题 | 不注入 | 仅保留在 corrections.md |

#### B5.4 询问用户确认（保守模式）
对每条计数≥2的教训，AskUserQuestion：
```
"教训'[标题]'已出现2次，建议注入到[注入路径]。
  现象：[发生了什么]
  教训：[以后怎么做]
  - ✅ 注入到 [SKILL.md 铁律 / 历史教训 / 设计规范摘要 / 子智能体Prompt模板]
  - ⏸ 暂不注入，继续观察
  - ❌ 不需要，删除此教训"
```

**用户选 ✅ 时的注入操作**：
- **路径A（铁律）**：SearchReplace 在铁律章节末尾追加新条目，同时在历史教训章节追加并标注"已升级为铁律第X条"
- **路径C（历史教训）**：SearchReplace 在"历史教训与防复发规则"章节末尾追加
- **路径C变体（设计规范）**：SearchReplace 在"设计规范摘要"内嵌区域中追加规则
- **路径C变体（子智能体Prompt）**：SearchReplace 在 Step B2 的子智能体Prompt模板中追加规则

用户选 ⏸ → 保留在 domains/，计数继续
用户选 ❌ → 从 corrections.md 移除

#### B5.5 反思 + 清理
1. 写入 `~/self-improving/reflections.md`：
```
## [日期] — 功能点→测试用例 [模块名]
CONTEXT: 生成N个用例，增强覆盖率M%
WHAT_WENT_WRONG: [哪些步骤失败最多/耗时最多]
LESSON: [下次执行改进什么]
INJECTED: [注入了哪些教训到技能本体] / 无
STATUS: ✅有注入 / ⚠️仅有记录
```
2. 已注入教训 → 移到 `~/self-improving/archive/`，在 domains/ 中记录引用
3. 未达2次教训 → 写入 `~/self-improving/domains/fp2tc.md` 的"待观察教训"
4. 更新 `~/self-improving/index.md` 行数统计
5. corrections.md > 30条时触发压缩（合并同类、归档已注入）
